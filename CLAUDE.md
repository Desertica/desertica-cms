# Desertica CMS

Strapi 5 (TypeScript) backend for the Desertica website and its internal content tools. The Angular frontend is `Desertica/desertica-web`; it reads this CMS on the server and keeps static defaults for everything. Read `README.md` (setup), `CONTRACT.md` (the fields the frontend depends on) and `docs/DEPLOY.md` (deployment).

## Commands

```bash
cp .env.example .env && npm ci   # fill the secrets (cloud sessions do this in a SessionStart hook)
npm run develop                        # http://localhost:1337/admin, first run seeds an empty database
npm run typecheck && npm test && npm run build   # what CI runs
npm run seed-check
```

Use **Node 22**. Create the first admin with `npx strapi admin:create-user ...` or through `/admin`.

## Model

The admin is for Spanish-speaking editors: sidebar names (`displayName` in each `schema.json`), field labels, hints and form layouts are in Spanish. Sidebar groups: `Sitio` (datos de la empresa, colores y estilo, reglas de reserva, formularios, menús), `Catálogo` (destino, tour), `Textos` (texto de la web), `Medios` (imagen o video de la web), `Páginas`, `Blog`, `Tienda`. Reservations and contact messages are not stored here: they live in `desertica-api` and the backoffice. Labels and hints live in `src/admin-es.ts` and layouts in `EDIT_LAYOUTS` in `src/content-manager.ts`; they change only what the editor sees, never an API id or field name. Locales: `en` (default) and `es`. `translation` and `media-slot` rows are segmented by `page` and `section`.

## Rules

- API ids (`singularName`, `pluralName`, uid) and field names are a contract with the frontend mapper; changing one needs a matching change in `desertica-web` (`src/app/core/cms/`) and in `CONTRACT.md`.
- `seed/catalog.json` is generated by `scripts/build-cms-seed.mjs` in the frontend repo (`npm run cms:seed` there); never hand-edit it. The catalog is seeded once on a database that was never seeded (`catalog-seeded` mark in the store); the legal pages are seeded as drafts. What runs on every boot, in order: `ensureLocales`, `grantPublicPermissions`, `restrictEditorRole` (once per version of its store key), `configureContentManager` (until `CM_CONFIG_VERSION` is applied without errors), `seedCatalog` (honors `SEED_ON_EMPTY`), `syncNewTranslations`, `ensureExtraPages` (once).
- Content tied to tours or destinations lives in their own fields; do not duplicate it as `translation` rows.
- `populate=*` does not reach media inside components; use explicit populate paths (see `CONTRACT.md`).
- The Editor role (set once by `restrictEditorRole`) edits and publishes tours, destinations, pages, blog, products, texts and media in `en`/`es`; only a Super Admin deletes tours, destinations and pages, and the Editor has no access to `Sitio`. `scripts/verify-editor.mjs` checks it in CI.
- A tour is active as a whole: unpublishing it in one language unpublishes every language (`src/tour-status.ts`). Publishing stays per language. The API (`POST /tour-refs/sync`) deactivates tours no longer published and creates new ones inactive; reactivating is manual in the backoffice.
- The second number of "Datos de la empresa" is `phone2` (to call); `whatsapp2` is obsolete, hidden, and `migrateWhatsapp2` copied its value once. `tour.pricePen` is the optional price in soles the website shows when the visitor picks soles.
- Tour text is `body` (one field, blank line = new paragraph). `lead`, `paragraphs` and `expandedParagraphs` are hidden in the form and only read by the website when a tour has no `body`; `migrateTourBody` filled `body` from them once, without touching them.
- Custom fields of the admin (`src/admin/fields.tsx`, registered in `src/admin/app.tsx` and `register()` of `src/index.ts`): `icon-picker` (`shared.feature.icon`: shows the drawing of each icon of the attribute's `enum`, the 28 in `src/admin/icons.ts`; it is an enumeration, so `migrateIcons` keeps working), `map-link` (`tour.meetingPointUrl`, preview from OpenStreetMap only when the link carries coordinates; `src/map-url.ts`), `format-select` and `focus-select` (`tour.format`, `tour.imageFocus`). They store the same plain strings as before (`lucideCar`, `both`, `center`), so the API and the website did not change; `format`, `imageFocus` and `meetingPointUrl` keep a `regex` instead of the enum check, enforced when publishing like every Strapi 5 rule (the error text is Strapi's English one). A new icon needs its drawing in `icons.ts`, its value in `feature.json` and its registration in the website (`FEATURE_ICONS`).
- Editor field lists: `fillEditorFields` fills empty lists once; `topUpEditorFields` adds fields that are new since the last boot (e.g. `tour.body`) without bringing back one an admin removed. Without a field in the list the form shows it as "no permission".
- The Public role is read-only. Keep it that way: the website never writes to Strapi.
- Never commit `.env`, `.tmp/` or `public/uploads/*`.

## Pitfalls

- Long texts (`page.body`, `blog-post.content`, `product.details`, `tour.waiverBody`) use the CKEditor 5 custom field with the Markdown preset: the stored value is still Markdown. Tours, destinations, posts and products translate themselves: every save of the Spanish version rewrites the English draft with DeepL (`registerAutoTranslate` in `src/translate.ts`, needs `DEEPL_API_KEY`, skips saves where the Spanish text did not change). The manual "Traducción automática" panel (`src/admin/translate-panel.tsx`) remains only for site texts, media slots, booking settings and menus. Pages (legal texts) and `tour.waiverBody` are never sent to DeepL.
- Content Manager list layouts, labels and hints are applied once at bootstrap (`CM_CONFIG_VERSION` in `src/content-manager.ts`); bump it to reapply. A field missing from an `EDIT_LAYOUTS` entry disappears from the form, so list every field of the type (a test compares each `schema.json` with the layouts). The panel look (Spanish locale, olive theme, logos) is `src/admin/app.tsx`.
- Theme colors are hex strings from the official color picker custom field (`plugin::color-picker.color`, regex `^#[0-9a-fA-F]{6}([0-9a-fA-F]{2})?$`); fonts, radius and header size are enumerations. Edit-view layouts and hints for `theme-setting` and `theme.palette` live in `EDIT_LAYOUTS`/`COMPONENT_LAYOUTS` in `src/content-manager.ts` and `src/admin-es.ts`. The seed converts the frontend's oklch values to hex in `build-cms-seed.mjs`.

- Admin extras: `config/admin.ts` enables Preview only when `CLIENT_URLS` and `FORMS_PROXY_SECRET` exist (site = first `CLIENT_URLS` entry, key = `FORMS_PROXY_SECRET`, signing in `src/preview.ts`; the website verifies the same `?preview=<exp>.<sig>` with the same key); `FLAG_NPS`/`FLAG_PROMOTE_EE` are fixed off there; the home widgets live in `src/admin/widgets.tsx` and read `GET /desertica/overview` (`src/overview.ts`); the tour checklist panel (`src/admin/checklist-panel.tsx`) and the widgets share `src/tour-gaps.ts`. Widgets are registered in `register()` of `app.tsx` (the `bootstrap` hook does not get `app.widgets`).
- E-mail: the nodemailer provider in `config/plugins.ts` is only for admin password recovery and is set only with `SMTP_HOST`.

- Editor simplification (`src/editor-rules.ts`, `HIDDEN_FIELDS` / `READ_ONLY_FIELDS` in `src/content-manager.ts`): external-address fields (`imageUrl`, `galleryUrls`, `itineraryFileUrl`, `coverUrl`...) and `tour.languages` stay in the schema for the website but are out of the edit layouts; `tour.priceFrom`/`pricePen` (prices live in the booking system; the website reads `GET /public/tour-prices` and only falls back to these) and the SEO title/description of tours, pages and posts (the website builds them from the title and lead) are hidden too; slugs of tour, destination, blog-post and product start from the title on create, follow the English name (`slugFromEnglish`) until the entry is first published and are locked for non-Super Admins; tour and product galleries hold at most 6 photos; `shared.feature.icon` is an enumeration (old free-text values are migrated at boot); `site-setting.placeholderImage` is uploaded once at boot (`src/placeholder-image.ts`) when empty.

## Ramas

`main` es solo la base; el trabajo entra por PR a `develop`, `develop` -> `staging` (pruebas) y `staging` -> `prod` (producción). Rama de trabajo: `feat/*`, `fix/*` o `chore/*`, se borra al mezclar. Los checks y la protección están en `docs/PROTECCION-RAMAS.md`; los workflows son `.github/workflows/{ci,security,policy}.yml` y los editas con un PR normal.
